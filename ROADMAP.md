## Graph view

From external user feedback (Discord, 2026-08-02): opening arbitrary Havok XMLs gives isolated, disconnected nodes instead of a fully connected reconstruction of the file. Confirmed — the graph is built from hardcoded class/param whitelists, not a generic reference walk.

- [x] **Split ref arrays on all whitespace, not just spaces.** Havok's XML writer wraps long `numelements` payloads across lines, so tokens like `#0137\n\t\t\t#0141` fail to resolve and states/transitions silently vanish. Every graph-side split uses `Split(' ')` (`StateMachineGraphView.xaml.cs:2135, 2318, 2418, 2432, 2446, 2707, 2722, 3727, 3746, 3775, 3780`; `BehaviorTreeBuilder.cs:87`) while the patching layer already splits on `{' ', '\n', '\r'}`. Likely the single biggest cause of "disconnected" on vanilla files; ~a dozen one-line changes.
- [x] **Replace the param-name whitelists with a generic `#ref` walk.** `WalkGenerator` follows only six param names, so every `BS*Generator` subtree is a dead end (`pDefaultGenerator`, `ChildrenA`, `pClipGenerator`, `pBlenderGenerator`, `pOffsetClipGenerator` aren't on the list — and these are all over `1hm_behavior` and magic/paired behaviors). Same limitation in `GeneratorChainContains` and `BehaviorTreeBuilder.IsLinkParameter`. The generic machinery already exists unused: `HavokManager.ResolveParams` resolves every `#ref` for every class at load, and `HavokValidator` builds a complete edge list for orphan detection then throws it away.
- [x] **Keep all inbound edges to shared children.** `WalkGenerator` returns on `visited.Contains(objRef)` *before* adding the parent→child edge (`StateMachineGraphView.xaml.cs:2381`), so a modifier/clip shared by N parents (normal in Havok DAGs) only ever shows its first edge. Move the visited check after edge creation.
- [x] **Seed the graph from the file's declared root, not `hkbStateMachine`.** A file with no `hkbStateMachine` yields a silently empty canvas, and the ⚙ root button requires `hkbBehaviorGraph`. Fall back to `HavokManager.RootObject` / `TopLevelObject` (the `hkRootLevelContainer`) so ragdolls, skeletons, and non-Skyrim Havok XMLs still graph, and show a "nothing to display" message instead of a blank canvas when there's truly nothing.

## Property editor (Object Data)

Same feedback round: the editor is not type aware — any text "yolo saves" into any field, and arrays can't be edited structurally.

- [x] **Type-aware param editing.** `HkParam` is stringly-typed and every field is a bare TextBox committing each keystroke (`MainWindow.xaml:1488`, nested at 1563); the only "type awareness" is a converter sniffing whether the current value is literally `true`/`false`. The typed metadata already ships in `libs\HKX2Library\HKX2\Autogen\` (all classes + enums) but `ModifierCatalog.CreateDefault` discards it on re-deserialization. Carry the HKX2 member type onto `HkParam` and key the editor template on it: numeric box for `hkInt32`/`hkReal`, ComboBox for enums, real CheckBox for `hkBool`. Done via `HavokTypeCatalog` (reflection + serialized-default enum detection) with live red-border validation on numeric fields.
- [x] **`EventResolver`-backed pickers for `*EventId` fields.** Follow-up to type-aware editing: event-id params were plain ints, so every one of them meant counting rows in the Events tab. `HavokTypeCatalog` now marks the integer params that are really table indices (`HkParamSemantic`) and the property editor edits them as name pickers — the file's own event or variable table as `name (#index)`, `(none)` for -1. Rules go by name because Havok gives no metadata: `*EventId`, `assignmentEventIndex`, and `id` on anything deriving from `hkbEventBase` (that last one is where notify events, clip triggers and event ranges keep theirs — 436 of them in vanilla `dragonbehavior` alone), plus `variableIndex` / `*VariableIndex` / `variableId` for variables. Nested params inside inline array elements included, so interval enter/exit ids and notify events get it too. An id the table doesn't cover renders as `‹unknown #N›` and is preserved — the picker list always contains the current value, which is what makes a cleared selection impossible to write back.
- [x] **Validate value types before save.** Save-as-XML writes garbage verbatim; save-as-HKX dies deep in HKX2's `int.Parse` with a generic "Save failed" and a misleading LE hint, and leaves the corrupt `.tmp.xml` on disk (`MainWindow.xaml.cs:2366-2397`). Add numeric/enum/bool checks to `HavokValidator`, run them from `BtnSave_Click`, and clean up the temp file on failure.
- [x] **Keep `numelements` in sync when editing array text.** The `Value` setter never touches `NumElements` (`HavokModels.cs:108-117`), and HKX2 treats the attribute as authoritative on conversion — hand-editing a ref list in the property editor silently truncates data, while the Edit States dialog maintains it correctly.
- [x] **Text edits to cached-ref params don't stick.** `HkParam.Value`'s getter returns the joined `Children` ids whenever resolved refs are cached there (single-`#ref` params, and one-element ref arrays like a single-entry `modifiers`). Typing in the property editor writes `_value` but the getter keeps showing the stale cached join, and save serializes from `Children` too — the edit silently doesn't stick. Found 2026-08-02 while scoping the numelements sync (which deliberately skips `Children`-holding params for this reason). Fix belongs in the setter: re-resolve the new ref(s) into `Children` — mutating a reference must update `Children`, not just `Value` (same rule the clip-preview editing follows).
- [x] **Generic array element add/remove.** Dedicated panels cover variables/events/states/transitions/clips/triggers, but the property editor has no add/remove/reorder for any array and there's no generic mechanism — e.g. `hkbStateMachineEventPropertyArray` (`enterNotifyEvents`/`exitNotifyEvents`) is entirely unhandled, and the Bindings tab is read-only. Add +/− on array params in the property editor, maintaining `numelements` and wiring new inline children correctly. Done for inline-struct arrays (＋/✕, HKX2-default or cloned elements, undoable); ref arrays edit as text end-to-end.
- [ ] **＋ Add element on arrays that are empty at load.** Follow-up: an empty inline array is indistinguishable from an empty ref array in the loaded data, so ＋ only appears once an array has (or had) an inline element. Distinguishing needs HKX2's TYPE_STRUCT vs TYPE_POINTER array metadata, which only exists in the autogen source comments / Read-WriteXml bodies — would need a small generated lookup or IL peek.

## Validation

- [x] **Events tab must maintain `eventInfos` alongside `eventNames`.** Bug found 2026-08-02 in capitto91's ThorMjolnir.hkx: the Events tab's `+ Add` appends to `hkbBehaviorGraphStringData.eventNames` but `eventInfos` has zero occurrences in the codebase — the `hkbBehaviorGraphData.eventInfos` array is never extended, so every event added through the tab desyncs the two arrays (his file: 30 names vs 26 infos; the runtime aligns them by index). The Variables tab does this correctly for its three arrays. Fix the add/delete handlers, and have the validator flag a names/infos count mismatch (it already checks the variable arrays).
- [x] **Validate `startStateId` points at an existing state.** Same file: `startStateId=1` with stateIds 2/3/4 — the machine has no valid start state and nothing warns. One-line check in the validator; also warn from the states editor when the start state is deleted.
- [x] **Orphan check misses refs inside inline children.** The validator's `allRefs` scan only reads top-level `param.Value`, so `hkRootLevelContainer`'s `variant` ref (inside the inline `namedVariants` struct) is invisible and `hkbBehaviorGraph` is falsely flagged as orphaned in every file. Walk inline children like the graph's `WalkParamRefs` does.

- [ ] **Pre-save "graph doctor" pass.** The domain's failure mode is silent (T-pose in-game, no error), and the editor already holds the data to catch the classics: states whose generator is null, dangling object references, transitions whose eventId is out of range for the event list, clip `animationName`s missing from the loaded character project's animation list, unreachable states, and an explicit "these N objects will be pruned on save" report instead of silent dropping.
- [ ] **Refuse to save a graph that fails a structural check — and port Community Behaviors' four.** Cassie's `docs/behavior-relay/merge-consistency-validation.md` is the evidence that "it converted" proves nothing: on 2026-08-12 a case-insensitive `.hky` filename collision (`BFCO.hky` vs `bfco.hky`) let MO2's VFS merge two mods into a structurally inconsistent graph, her compiler accepted it and emitted a 490 KB `0_master` instead of 597 KB, and the game hard-faulted with no crash log and no log line — while offline the same input produced merely wrong-but-complete bytes, so every offline gate missed it. Four of her five checks apply here: **dangling node references** (state `generator`, SM `states[]` and `startStateId`, transition `toState`, blender/selector/modifier-list children, `rootGenerator`), **root generator resolves**, **`eventInfos`/`eventNames` and the three variable arrays agree on count**, and **`stateId` unique within each state machine** — the last is the one nothing here checks today, and it is what makes `toStateId`/`startStateId` ambiguous. A fifth, from the same work: **soft refs survive a delete** — reachability GC protects hard pointers (an unreferenced object is never written), but `toStateId`, event/variable name bindings and `animationBindingIndex` are bare ints and strings the runtime resolves later, so a graph that orphans a state while a surviving transition still points at it saves clean and fails in-game. Judge it on the final graph, after every edit is applied. The first three overlap the graph-doctor item above; what she adds is the *policy*, worth adopting wholesale: refuse rather than emit, and say in one line which graph, which ref failed, and the likely cause.
- [ ] **Behavior-reference awareness.** Follow-up to the 0.6 "New behavior reference…" action: double-click an `hkbBehaviorReferenceGenerator` to open the referenced file (the workspace knows the project root); flag a `behaviorName` path that doesn't resolve on disk; and check event-name alignment between referencing and referenced graph — the runtime link is by name, so "event used in the child file but missing from the parent's eventNames" is a silent no-op in-game today.

## Community Behaviors (ex-Behavior Relay) / `.hky` interop

Cassie's [Skyrim Content Tools](https://github.com/Cassieandstuff/Skyrim-Content-Tools) is building a **runtime behaviour compiler**: an SKSE plugin that compiles behaviour graphs from YAML in-process at load time and serves the bytes to the game, replacing the Nemesis/Pandora offline patch step. ### The identity contract, restated

`sop/behavior-relay-formats.md` supersedes this section's earlier "node records override by FormID, edge records compose additively" sketch. **Identity is `(owner, local-id)`** — the number alone is never identity. The bundle header declares its masters by *stem*, never a positional ordinal; per node, a `new` flag means owner = self, an explicit `Master::id` overrides that master's node, a bare unflagged id means the graph's **frozen base** (and a bare id the base lacks is a loud error, not a silent new node), and `delete` tombstones a membership edge. Containment is inverted — the child names its parent (`parents:`, `entryTransitions:`), so a bundle inserts a state into vanilla without ever editing the id-keyed vanilla node. Lateral refs (a transition's `toState`, a generator input) are bare = the frozen base, by local name = your own new node, `Owner::id` = a deliberate cross-mod patch. **Names are a label and a drift-audit checksum, never a merge key — except events, variables and character properties, which are a shared symbol table and do bind by name.** Upstream status: the invariant is locked, the implementation is partial (the loader still keys `(class, bare-id-or-name)` with no owner axis).

Two of her facts stay load-bearing for us. **Havok node names are not unique** — vanilla ships duplicate `pa_KillMove*` and a triple `CrossBow_IdleDrawn`, and BFCO shares its `Bfco_AttackPower123_*` combo states across two state machines — and name-as-identity cost her an in-game crash (two same-named states collapsed in a name-keyed map, leaving a null child on a killmove `hkbModifierGenerator`), a shared state silently split in two (it presented as iceskating), and +407 objects of de-sharing bloat on `1hm`. Anywhere this editor keys on a name rather than an id is exposed to the same class of bug. And **packfile object order is meaningless**: references are `_localFixups`/`_globalFixups` patched to real offsets at load, vanilla's own `1hm` object list is interleaved rather than grouped, and her merged BFCO graph — in a layout matching neither vanilla nor Pandora — runs combat in-game. That independently confirms the "harmless for the game" call on the ragdoll id-shift item below. `hkbNode::id` is written to disk as the placeholder `0xFFFF` and assigned by the engine at `Activate`, so it is not identity either.

Her merge work adds one check to the four in **Validation** above: reachability GC protects *hard* pointers (an unreferenced object is simply never written by the serializer), but `toStateId`, event/variable name bindings and `animationBindingIndex` are **soft refs** — a graph that orphans a state while a surviving transition still carries its `toStateId` writes fine and fails at runtime. Judge it on the final graph, after every edit is applied.

### Division of labour — what crosses, and what doesn't

Her behaviour graph panel is still a literal `"Behavior Editor — not yet implemented"` ImGui stub at `f5ddbaa`, 354 commits in — the authoring GUI is the half she isn't building, and it is the half this is. So the collaboration has a shape without either project absorbing the other, and while her licence is provisional (see above) what crosses is **formats, findings and data — never code, in either direction**.

It also buys a say in the schema both projects would then be reading.

- [ ] **Audit every name-keyed map in the editor and key on id.** Her three name-as-identity bugs (crash, iceskating state-split, +407 objects of bloat) are ours to inherit wherever we do the same — `EventResolver`, the graph view's node lookups, `StateDuplicator`, patch snapshot matching. **Two constraints on the bridge.** First, mind what is still moving. ### Answered by her directly, 2026-09-05

Four questions this section had open are now settled, from Cassie in conversation rather than from the repo:

- **`Skyrim.hky`'s id space is canonical, and deliberately so** — "it had to be in order for Nemesis compat to work." So an override written from here carries her base's ids, and those are the tagfile `#NNNN` ids. That makes the C# tagfile-oracle item above a *prerequisite* for export, not a parallel nicety: without the mapping we cannot address a vanilla node at all.
- **New nodes are authored by name, and the compiler mints the id.** Adding a state to an existing state machine means dropping `<mod>_mynewstate.yaml` into the unit; nothing here ever invents an integer id. That removes the one piece of the exporter that looked genuinely hard, and it means the editor's existing name-based authoring flow is already the right shape for new content — the id discipline above matters for *overrides* and for our own internal keying, not for minting.
- **The `Havok/` schema is sufficient to write the YAML** — "the havok/ root directory should have everything it needs in order to write the actual yamls." So the exporter should be **driven by her descriptors** rather than hard-coding a field list per class: read `name`/`parent`/`fields` and emit. Behaviour classes are migrated already; other families are still moving over, so behaviour is the slice to build against.
- **Merge semantics are moving into the same schema** — each class declares how it merges onto itself on a node collision (the `merge:` field policies). A tool that produces deltas therefore gets its conflict rules from the same data it gets its layout from, rather than reimplementing a merge engine.

**One practical licence consequence.** Her descriptors are the natural input for all of this, and they live in an all-rights-reserved repo. So read them from the user's own SCT checkout or from a bundle at runtime — do not vendor a copy into this GPL-3.0 tree while her licence is provisional. Same rule as her code: use the format, don't ship her files.

- [ ] **Open the load order and edit as deltas — the Creation Kit model.** Her suggestion, and the largest thing in this section: point the editor at the user's load order, compose the bundles with the schema's own merge semantics, present the *merged* graph as one project, and write every change as a delta into a new or active `.hky` — the CK's active-plugin model, applied to behaviours. It is the right end state and it is not a bolt-on: it needs a composed document model (today one file is one packfile), an active-bundle concept with per-object provenance ("who introduced this node, who overrode it, am I about to override or author"), and a decision about whether it converges with the Nemesis snapshot exporter or stands beside it as a second, separate delta mechanism. Worth sequencing behind the four import fixes and the oracle, both of which it depends on, and worth prototyping read-only first: compose a two-bundle load order and *show* the merged graph with provenance, before anything writes.

## Save / IO

- [x] **Skyrim LE (32-bit) support, and LE ⇄ SE conversion.** LE and SE share the Havok schema (`hk_2010.2.0-r1`, class version 8) and differ only in packfile pointer size, so conversion is a pure repack — but the bundled HKX2Library had been de-generalised to SE, with 908 padding constants across its 588 generated classes baked to an 8-byte pointer. `tools/hkx-layout-gen` re-derives Havok's layout rules from each class's own metadata and re-emits the padding as `des.Padding(pad64, pad32)`, refusing to emit anything it can't first reproduce byte-for-byte at 64-bit (so SE output is unchanged by construction). Surfaced two real bugs: `hkUlong` members (`hkbNode.m_userData`) read as fixed 64-bit, and `ALIGN_16` members not honoured where the 64-bit layout was already 16-aligned. Validated on all 180 loose vanilla LE files — all parse, all round-trip LE→SE→LE with byte-identical Havok XML (`tools/hkx-roundtrip`). Nineteen classes remain 64-bit-only (`hkp*`, type-metadata classes, `hkbGeneratorSyncInfo`); none occur in behaviour/character/project/skeleton/animation files, and writing LE is refused with their names rather than producing a corrupt file. Done 2026-08-21.

- [ ] **hkxcmd-compatible object numbering for XML export.** Havok binaries don't store `#NNNN` names — the converter invents them, and ours disagrees with the one Nemesis/Pandora patches are keyed to. HKX2's `XmlSerializer` counts from `#0050` in reference-graph order (root first); hkxcmd numbers from a computed base in a different order. So XML exported from a `.hkx` here can't be used with engine files that reference object ids. Blocked on the ordering rule (see below); **do not ship an approximate version** — ids that are close but wrong make patches silently target the wrong object, which is worse than ids that obviously differ.

  Solved so far — the **base index**, exact on 9/9 vanilla LE files:
  `base = |transitive class closure| + |distinct enums declared in those classes| + 1`,
  where the closure starts from the classes in the packfile's `__classnames__` section (minus `hkClass`/`hkClassMember`/`hkClassEnum`/`hkClassEnumItem`) and follows base classes and member types. Havok numbers reflection metadata first — one `hkClass` per class, one `hkClassEnum` per enum — so the first data object lands at `C+E+1`. Confirmed by two files with different class/enum splits but the same `C+E` (57+18 and 58+17) getting the same base, 76. Bases seen: project 8, character 22, animation 45, behaviour 76–100, ragdoll skeleton 128.

  Unsolved — the **ordering**. The root takes the lowest id and its own child (`hkbBehaviorGraph`) the highest, so it's broadly post-order with the root special-cased, but no candidate reproduces it. Scored against hkxcmd on dragonbehavior (1455 objects): post-order + reverse member order with the root hoisted matches the first 4; root + reverse packfile-layout order matches the first 5 (and is *exact* on 5-object animation/character files); post-order + reverse as-is matches hkxcmd's **document** order for 32, showing write order and id assignment are two separate passes. The Havok SDK is closed and isn't bundled in `Tools/hkxcmd-master` (only hkxcmd's calls into it), so the rule has to be derived empirically. `tools/hkx-idorder` is the scoring harness for resuming.

  **A different route to the same mapping, found 2026-08-30 in Cassie's repo** (see Community Behaviors / `.hky` interop): don't reproduce hkxcmd's traversal at all — recover the correspondence structurally. Deserialize the binary recording each object's outgoing refs in `Read`/field order, parse the tagfile recording each `#NNNN`'s refs in document order, then co-DFS from both roots in lockstep matching refs positionally. The graph shape is identical on both sides, so it yields `binary-offset → #NNNN` for every object: **2418/2418 on vanilla `0_master`, zero class mismatches.** Implemented there as `havok-core-cli idalign`. It needs a tagfile as input, so it recovers a mapping rather than minting ids from nothing — it does not close this item on its own. What it does close is the fallback: "convert with hkxcmd first" stops being advice and becomes a mechanism, and it is what makes Nemesis patch import tractable (her `ConvertPatch` keys the merge on exactly these ids, proven over the whole BFCO humanoid set). The one operational trap: the binary and the tagfile must be the *same* extraction — a one-object drift desyncs the positional walk from that point down.

  Lower-effort alternative if this stays blocked: warn on XML export from a `.hkx` that the ids won't match Nemesis, and point users at converting with hkxcmd first. Note the editor already preserves ids and `toplevelobject` verbatim through XML load→save (verified on hkxcmd-numbered dragon/magic/horse behaviours and skeleton — `tools/hkx-idpreserve`), so "convert with hkxcmd, edit here, save XML" is already id-safe. Raised 2026-08-21 from a community report that SSE→LE converted files mis-patch under Nemesis.

- [ ] **Ragdoll files shift object ids on repack.** Re-running hkxcmd over a file this tool repacked reproduces vanilla ids exactly for 24 of 25 sampled LE files — the exception is `skeleton.hkx` (207 objects, almost all `hkp*`), whose ids shift because HKX2 writes fixups in a different order than the original exporter (a pre-existing library quirk its README already notes). Harmless for the game, but it means a ragdoll converted here can't be patched against vanilla-derived ids. Nemesis patches behaviours rather than skeletons, so impact is limited. Found 2026-08-21 alongside the numbering work above.

- [x] **Stop writing empty `numelements=""` attributes in XML saves.** `HkParam.NumElements` defaults to `""` and had no `ShouldSerialize` guard, so the XmlSerializer emitted it on every param whether or not it was an array — 18,884 spurious attributes in vanilla `dragonbehavior.hkx` (1512 objects). Harmless to the game, but app-saved XML differed from converter output on virtually every line, which made hand-diffing a save against hkxconv/temp XML — how the id and layout work gets checked — useless. `ShouldSerializeNumElements()` suppresses the attribute when blank; blank already meant "not an array" to `HavokTypeCatalog.Annotate` and `ResyncNumElements`, and a genuinely empty array keeps its explicit `"0"`. Round-tripped `dragonbehavior.hkx` through the real save path: attribute set now matches HKX2's own serializer exactly (958 both sides, all 232 `"0"` counts kept, zero empty), and normalised diff noise against converter output fell from 61,917 differing lines to 20,189 — the rest being the root's `xmlns:xsi`/`xsd` and long-array line wrapping, both separate issues. Since the count is authoritative on XML→HKX, the full loop was run through the real save method too — .hkx → XML → save → .hkx → XML returns byte-identical to the original conversion, same 369,616-byte binary, nothing truncated. Found 2026-07-29 while verifying trigger editing end-to-end; done 2026-08-27.

- [x] **Saved XML reproduces the converter's output.** Follow-up to the `numelements` fix above, which uncovered that the empty-attribute leak was one of a family. Three more, all in the same direction — the editor wrote things Havok's own writer never does: inline (anonymous) `hkobject`s got `name="" class="" signature=""` (2,798 per behaviour file) because `HkObject` had no `ShouldSerialize` guards either; the root element got `xmlns:xsi`/`xmlns:xsd` from the default XmlSerializer; and empty array params self-closed as `<hkparam … />` where Havok writes `<hkparam …></hkparam>` (the converter uses the full end tag in 500+ places across the sample and self-closes exactly once, on one `quadVariableValues` — an HKX2 quirk we now differ from, which is the right trade). A fourth was a genuine bug rather than cosmetics: **saves rebuilt the packfile from `ObjectMap` and never carried the header over**, so every save wrote `classversion="" contentsversion=""`, and `toplevelobject` was empty from `HavokWorkspace.SerializeManager` (character/project saves) or hard-coded `#0050` from `MainWindow.SerializeToFile` — the root is `#0050` only by convention, and a wrong `toplevelobject` points the runtime at the wrong object. `HavokManager` now retains the header at `BuildGraph` and hands it back through `NewPackfile()`, falling back to Skyrim's schema only for a from-scratch file; all writes go through `HkXml.Write`. Measured over 9 vanilla files (behaviour, character, project, skeleton; 71,930 lines of XML): zero empty attributes, zero namespaces, header matching the converter on every file, and **65 differing lines left in total** — down from tens of thousands. Every file still round-trips XML → .hkx → XML byte-identical to the original conversion. Done 2026-08-27.

- [ ] **Preserve HKX2's `SERIALIZE_IGNORED` comments through load → save.** The converter annotates every member it deliberately doesn't serialize (`<!--memSizeAndFlags SERIALIZE_IGNORED-->` and friends) — 14,125 of them in `dragonbehavior.hkx`, which is the entire remaining line-count gap between a save and a conversion (44,807 vs 30,682 lines; the difference is exactly the comment count). The model doesn't represent XML comments, so they're dropped on load. Low priority and possibly not worth doing: they carry no content, HKX2 regenerates them from class metadata on every `.hkx`→XML conversion, and filtering them (`grep -v '<!--'`) makes a diff exact today. Doing it properly is awkward — `XmlSerializer` can capture comments with `[XmlAnyElement]` but won't interleave them back among `hkparam` elements in document order, so it needs a custom writer, not a model tweak.

- [ ] **Two structural differences from converter output remain.** (1) An inline `hkobject` with no params writes `<hkobject />` where Havok writes `<hkobject></hkobject>` — 32 per skeleton file, 64 diff lines, and the only structural difference left in the sample. The `hkparam` half of this was fixable by always emitting the text node, but `HkObject` has no text member; adding an `[XmlText]` one was tried and is **the wrong fix** — mixed content makes `XmlSerializer` abandon indentation entirely, which took `dragonbehavior` from 0 differing lines to 30,251. The real fix is a delegating `XmlWriter` whose `WriteEndElement` calls `WriteFullEndElement`. (2) The XML declaration says `encoding="utf-8"` where the converter says `us-ascii`. Deliberately not matched: `XmlSerializer` writing through a `StreamWriter` takes the declaration from the writer's encoding, and an ASCII `StreamWriter` would replace non-ASCII with `?` rather than escaping it — and non-ASCII does occur (HKX2's U+2400 null-string sentinel). One diff line, and utf-8 is the safer of the two.

## Animation / clip preview

- [ ] **Export an animation as FBX.** Read-only preview is half a bridge: you can
  watch a clip but not take it anywhere. `tools/hkx-fbx-export` is the harness —
  it feeds `HavokSplineDecoder`'s `[frame][bone]` locals plus the project
  skeleton into a hand-written FBX writer, and `--selftest` drives a synthetic
  720°-spin clip over a real `skeleton.hkx` so the writer can be exercised
  without an animation on disk. Verified 2026-09-05 against the pddragon
  skeleton: Blender 4.5 imports it as an 84-bone armature with the right names,
  hierarchy, frame count and fps, and the spinning bone's total angular travel
  measures 720.00°.

  **Write the binary form, not ASCII.** The first cut wrote FBX 7.4 ASCII on the
  theory that it is readable and universally accepted; Blender answers "ASCII FBX
  files are not supported" and refuses the file. ASCII now survives only behind
  `--ascii` as a debug view of the same record tree, which is why the tree is
  built once and serialised twice.

  Two things the format forces and one it doesn't settle. FBX animates rotation
  as **Euler**, so every quaternion is converted (eEulerXYZ, R = Rz·Ry·Rx) and
  unwrapped against the previous frame — without the unwrap a wrapped atan2 reads
  as a one-frame spin, which is the same "wrong on some frames" symptom a decode
  bug gives. Every channel is keyed on every frame rather than re-fitted, since
  the decoder already evaluates the spline per frame and a second fit is a second
  place to be wrong. Unsettled: **the Havok-unit scale.** Nothing in the file says
  what a unit is worth; the dragon's rest pose spans 1097 × 1333 × 301 units, and
  Blender reads `UnitScaleFactor 1` as centimetres and divides by 100, so it
  arrives 10.97 × 13.33 × 3.01 Blender units. `--scale` exists for that and
  defaults to 1 rather than inventing a constant.

  Run against the 62 real troll animations in `C:\hkxworking_64	roll`: all 62
  export, and both a single-block and a multi-block clip round-trip through
  Blender to within 0.0004 Blender units and 0.12 degrees over 15,960
  bone-frames, which is float32 key storage rather than anything structural.
  That sweep is also what found the multi-block gap, now closed (below).

  Two findings worth keeping. A twist bone first reported a 159.61 degree
  single-frame Euler jump, which reads exactly like a decode bug; it was the
  parameterisation. Every rotation has two XYZ Euler spellings, and near the
  y = ±90 singularity — where twist bones sit — the naive one swings a channel
  most of a turn while the bone barely moves. Choosing per frame whichever
  spelling lands closer to the previous one drops it to 84.45, against a real
  worst-case motion of 47.44 degrees. And the residual Euler excess never
  reaches playback in Blender, which rebuilds quaternion curves at import; it
  would cost sub-frame accuracy only in a consumer that keeps Euler curves.

  Still open: scale tracks (the decoder skips them, so `Lcl Scaling` stays 1),
  and promoting this into an "Export to FBX" button on the clip preview.

- [x] **Multi-block animations decode.** `numBlocks > 1` was refused outright, so
  no clip longer than ~256 frames would preview. `HavokSplineDecoder.DecodeBlocks`
  walks `blockOffsets`, slicing each block so its offsets stay block-relative.
  The rule: consecutive blocks **share their boundary frame**, so a block advances
  the timeline by `maxFramesPerBlock - 1`. Measured rather than assumed — on
  `getupfaceup` (285 frames, 2 blocks) block 0's local frame 255 and block 1's
  local frame 0 are 1.90° apart against 8.32° for the next candidate and ~8°
  between ordinary neighbours: the same instant, quantised twice. Off by one here
  is what makes a clip play correctly for a few hundred frames and wrongly after,
  which is the shape of the community "wrong on some frames" reports.

- [x] **Trigger list panel in the clip preview.** The ☰ side panel gets a "Triggers" section under the annotations — time, frame, event name, relative-to-end marker — click a row to seek, edit time inline, Del to delete, right-click to add/edit/delete (event changes go through the trigger dialog, which knows the graph's event list).
- [x] **Add/edit/delete clip triggers on the timeline.** The orange ticks are editable like the purple ones: right-click/double-click to edit (event picker with create-new-event, time/frame, relativeToEndOfClip anchor), drag to move, timeline right-click to add. Creates and wires the hkbClipTriggerArray in the same undoable action when the clip has none; warns before editing an array shared by multiple clips.
- [x] **Annotation list panel in the clip preview.** Toggleable table (☰) of all annotations — time, frame, track, text — click a row to seek, edit time/text inline, Del to delete.
- [x] **Track picker for multi-track animations.** The Add-Annotation dialog shows a track dropdown when the file has more than one annotation track (single-track files keep the track-0 default silently).
- [x] **hkanno-format annotation import/export.** Copy/export the clip's annotations as hkanno's `<time> <text>` text format (the interchange format Precision/AMR modders already use), and import/paste a set back, replacing the file's annotations in one undoable step.
- [x] **Drag annotation ticks on the timeline.** Move an annotation by dragging its purple tick — frame-snapped, Alt for free placement.
- [x] **Add/edit annotations on the clip timeline.** The preview already reads an animation's `annotationTracks` and draws each annotation as a timed, labeled tick (purple), but they're read-only. Let users add a new annotation, edit an existing one's time/text, and delete one — useful for mods that drive behavior off annotations (e.g. Precision, Animation Motion Revolution). Requires a write-back into the animation's `annotationTracks` array: create the annotation through Children/InnerObject (not `Value`), and wire it into the track in the same action so it isn't pruned on `.hkx` save. Should be undoable like other object edits. Requested by a user.
