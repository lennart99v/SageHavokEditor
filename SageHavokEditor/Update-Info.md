Unreleased:

- A few more fields survive a YAML import intact. Some settings are written in the source by name where the game reads them by number — the variable a state machine syncs on, the events that start a pose match, the events that switch a modifier on and off. The import was keeping the name, which is not a field Havok has, so those settings simply weren't there: a modifier that never activates, a pose match that never starts. They are now resolved to the numbers, and the editor works out which fields those are by asking Havok's own class definitions rather than from a list, so the same will hold for any similar field in a source tree written later.

- Clip triggers now survive opening a YAML behavior folder. A trigger is how a clip tells the rest of the graph where it is — the moment a hit lands, the moment an unequip is far enough along to move again — and in the source they are written straight onto the clip, where Havok expects them in a small object of their own that the clip points at. The import was building them correctly and putting them in the wrong place, which the file happily saved as XML and then failed to convert with a nonsense error about a missing reference whose name was every value in the trigger run together. That affected 202 of the 289 clips in vanilla 0_master and 163 of the dragon's 214 — in other words, essentially every clip that drives anything off its own timeline. Event names are resolved to the numbers the game reads (554 of them in 0_master alone), and a trigger's payload — the "Left" in a HitFrame that says which hand — becomes the small object it is supposed to be rather than text on a field that doesn't exist.

- Opening a YAML behavior folder now produces a file the rest of the editor treats like any other. Two things were missing and neither was visible until you tried to save. A Havok binary is read through a single root container that names the graph — nothing in a YAML source tree describes it, because it is not behavior, it is the envelope — so an imported folder had no root, and the file it saved announced a root object that was simply whichever object happened to be numbered fiftieth. Saving to XML worked; saving to .hkx died before it had read a single line of content. The import now builds that root properly and carries the Havok version numbers from behavior.yaml instead of assuming Skyrim SE's. The second thing is quieter: an import never picked up Havok's type information, so every field in Object Data was a plain text box — no numeric checking, no dropdown on an enum, no event picker where a number is really an event. It goes through the same path a loaded .hkx does now, so all of that works on an imported folder too.

  Saving an imported folder to .hkx still doesn't finish, and this is the honest state of it: the conversion now gets past the header and stops on the first thing in the content it can't read, which is a different thing in different files — clip triggers in 0_master, a transition condition in mt_behavior, a blender's children in dragonbehavior. Those are being worked through one at a time, and each has its own roadmap item now rather than being one vague "it doesn't convert".

- Object Data can now add elements to an array that arrived empty. The ＋ Add element button used to need an element already there to recognise the array by, which meant the arrays that most often need filling in were the ones you couldn't touch: a behavior graph's character properties and its word min/max value sets, a look-at modifier's eye bones, a keyframe modifier's bone list, the properties on every rigid body in a skeleton. All of those ship at zero elements, and the only way to add one was to save to XML, edit it in a text editor and load it back. The reason it was hard is that an empty array tells you nothing about what belongs in it — an array of nested objects and an array of references to other objects look exactly the same on disk once there's nothing in them — so the editor now asks Havok's own class definitions instead of guessing from the file, and knows the difference before you've added anything. New elements come out with Havok's own default values for that element type, all in one undoable step that keeps the element count in step with the contents. The flip side is that reference arrays no longer offer the button at all, rather than merely happening not to: those are still edited as a list of #ids in the text box, which is what they are.

- When a clip names an animation your character file doesn't know about, the editor now offers to register it on the spot. This is the other half of a trap that has caught everyone at least once: the behavior graph names an animation by path, but the game loads it through the character file, so doing only the first half gives you a clip that plays nothing — silently, with no error and nothing in a log to explain it. The offer appears wherever you choose the path: creating a clip generator from the graph, creating one on the Clips tab, or browsing to a new animation for an existing clip. Say yes and it is added in one undoable step, and the status bar reminds you the character file is a separate file that still needs saving. It stays out of your way otherwise — nothing appears if no character file is open, if the path is blank, or if the animation is already registered.

- A reminder that first person is a different project. The player is really two behavior projects: the one you have open under actors\character\, and a completely separate one under actors\character\_1stperson\ with its own master graph, its own event list and its own animations. Nothing connects them, so a patch you make here does not reach the view down your own arms — and the way that fails is nasty, because it works perfectly in third person, and switching view just quietly does nothing. There is no error to find. So the editor now says so at the two moments it matters: when you export a patch, and the first time you author a behavior reference in a session. Only for the player's own project — dragons and horses have no first-person view, and if you already have the _1stperson files open it says nothing, since you are already there.

- A behavior reference can now be followed, and the editor reads what is on the other side of it. The reference node is the one place a graph stops being about this file — it is how vanilla splits 0_master across a dozen behavior files, and how every Nemesis or Pandora patch bridges into a mod's own graph — but its path was just a string sitting in a box, and finding the file it named was your problem. Double-click the node in the Graph tab, or right-click it and choose Open, and the editor resolves the path the way the game does: relative to the character project's root, ignoring case, and finding a .xml where the path says .hkx, which is what a project looks like halfway through being edited. When nothing matches it tells you which folders it looked in, because a path relative to a folder the file never names is otherwise unguessable.

  The validator now says one thing about references: a path that resolves to nothing is reported, because in-game that is a state which plays nothing, with no error, no crash and no log line. It never refuses a save — whether a file sits on your disk says nothing about whether the graph itself is sound, and if you work through a mod manager the referenced file legitimately lives somewhere the editor cannot see.

  The other half is a comparison you ask for rather than one you are told: right-click a reference and choose Compare events with referenced file. The two graphs are linked by event *name* and each keeps its own separate table, so the dialog lays both tables side by side, marks which side declares each name and which side actually uses it, and can filter down to the ones that cannot cross the reference. This started out as a warning and the evidence talked it out of that: run it against vanilla Skyrim's own 0_master and ten of its thirteen references have events the parent has never heard of — one of them 418 of them — on a file the game runs perfectly. A child behavior's internal events are simply its own business. So the numbers are worth having, and worth having only when you went looking for them, with the same caution the unreferenced-event list carries: leads, not faults. What it is genuinely good for is the reverse mistake, expecting an event to cross when it can't, which looks in-game exactly like everything working right up until the animation doesn't play.

- Saving to .hkx now stops if your edits have left the graph contradicting itself. Not a warning you can click past — the file simply isn't written, and the report tells you what broke and, under each line, what usually causes it: "the destination state was deleted, or its stateId was renumbered", "a state was copied into this machine keeping the original's stateId". The reason it works this way rather than asking is that a graph in this condition is accepted by everything downstream. It converts. The game loads it. Then an actor T-poses, or the process falls over, and there is nothing in any log to read. The moment before the file is written is the last one where the reason is still knowable, so that is where it gets said.

  What counts: a reference pointing at an object that isn't there, a state or blender child or root generator left null, an event id or variable index past the end of your tables, a startStateId or a transition target matching no state in its machine, two states in one machine sharing a stateId, and the paired name/info arrays disagreeing on length. Crucially, only the ones your session introduced. Vanilla files are not clean by this standard — Bethesda's own dragonbehavior has a duplicate stateId, two start states that don't exist and nine transitions pointing at missing states — so the editor records what was already wrong the moment it opens a file, and refuses only over what wasn't. Open a broken vanilla file, fix one clip, save: that works, exactly as before. Break something yourself and it won't. Everything else is unchanged: saving to XML still goes through the ordinary report with Save anyway, since XML is the working format rather than the thing the game loads.

- A graph doctor now runs before every save, and 🔎 Validate runs the same pass on demand. Havok never tells you when a behavior is wrong — there is no error, no crash and no log line, the character just T-poses — so a file that saved cleanly and converted cleanly can still be broken in every way that matters. The pass looks for the failures that actually happen: a state, a blender child or the graph's own root generator left pointing at nothing, so that node produces no pose at all; an event id or variable index past the end of this file's own tables, which the game reads by position and never bounds-checks; a clip naming an animation the character file never registered, which is what usually goes wrong when you add an animation and forget the other half; a state nothing can enter, because it isn't the start state and no transition targets its id — exactly what a duplicated state you haven't wired up yet looks like; and, finally said out loud, the objects an .hkx save is about to drop. That last one used to be reported as "orphaned object", which only asked whether anything referenced them; it now asks the question the save actually asks, which is whether the file's root can reach them, and two dead objects pointing at each other no longer slip through. Where the report can't be sure it says nothing rather than guessing: a machine that picks its state with a chooser, at random, or by stepping up and down the list is left alone, since any of its states can be entered.

  Before a save the report opens by itself, but only when there is a real structural error or something about to be lost — warnings on their own never interrupt you. Nothing here refuses to save; a graph half-way through an edit legitimately has states nothing reaches yet, and only you know whether that is a mistake. Cancel is the default button, so hitting Enter stops and lets you look rather than writing the file. On stock Skyrim content the pass is quiet apart from the things that genuinely are there — vanilla dragonbehavior has three objects the .hkx save drops and fifteen states nothing enters, several of them in machines whose transitions already point at ids that don't exist.

- The Add/Edit Transition dialog can create the blend a transition uses. Every transition points at a transition effect, and that object is what decides whether the switch blends or snaps — but the dialog never let you choose one. It quietly reused whatever effect it found first in the file, and when the file had none it wrote null, which is the normal state of a behavior made with New behavior file: every transition you added snapped instantly, with no setting anywhere to explain why. There is now a Blend row listing (none), every transition effect already in the file with its name, id and duration, and "＋ New blending effect…" with a duration box that defaults to 0.2 seconds. Pick that and the editor builds a proper hkbBlendingTransitionEffect — the rest of its settings come from Havok's own defaults, the same values vanilla files use — names it after its duration so it's recognisable later (Blend_200ms), and wires it into the transition in the same undoable step, so it can't be left as an orphan for the .hkx save to drop. A file with no effect at all opens the picker on "New blending effect" rather than on nothing, since that's the case where you almost certainly want one. The picker is on Edit too, which is how a transition you already authored gets a blend, and it always contains that transition's current value, so confirming the dialog can never quietly change which effect a transition uses. Durations are checked before they reach the file: a negative number or a typo is refused rather than written, and typing 0,2 works as well as 0.2.

  One thing fixed on the way: the From State, Event and To State dropdowns in that dialog were showing an internal class name whenever they were closed, and only the real names once you clicked one open. They read correctly now.

- Graph tab → right-click a state → "⧉ Duplicate state…". A custom behavior is usually a family of near-identical states — Aim, Throw, Recall, Catch off one clip pattern — and building the second one meant creating the state, its clip, its modifiers and its transition array by hand, object by object, with the domain's usual silent failure waiting at the end: miss one reference and the copy quietly drives the original's generator, which looks fine until both states animate as one in-game. Duplicate copies the state and everything hanging off it — the generator chain, the binding set, the enter/exit notify arrays, the transition array, and nested state machines with all their states — gives every copy a fresh id, and rewires the copies to point at each other rather than back at the originals. Two things are deliberately shared instead of copied: transition effects, because one hkbBlendingTransitionEffect normally serves the whole file and carries no per-state data, and the file-level singletons (the behavior graph, its data and string data), which the walk refuses to touch even in a hand-edited file that points at them. The dialog has two options and tells you how many objects each combination creates before you commit — a state whose generator is a nested machine can be 200-plus, which is worth seeing first: share the original's generator instead of copying it, and skip the transitions, where skipping means the copy starts with none rather than sharing the original's array (sharing it would make editing one state's transitions edit the other's). The copy gets a fresh stateId, unique within its machine, and is added to that machine's states list in the same undoable action — which is what keeps it out of the orphan-pruning .hkx save. Copies are renamed so nothing collides, carrying the rename through the subtree where it fits: duplicating Aim as Throw turns AimClip into ThrowClip. One thing to know afterwards — nothing transitions to the copy yet, because transitions route by state id and the copy has a new one, so add an incoming transition before you expect to reach it in-game.

0.6.0 Features:

- Saved XML now matches what the converter produces, and the packfile header is finally right. Chasing the numelements noise turned up that the same empty-attribute leak ran through the whole writer: every inline object was tagged name="" class="" signature="" (2,798 per behaviour file) where Havok writes a bare tag, the root element carried two xmlns declarations Havok never emits, and empty arrays were closed the short way instead of the long way. Underneath the cosmetics sat a real bug — a save rebuilds the file from the objects in memory and was never copying the header over, so every file written by the editor claimed an empty classversion and contentsversion, and toplevelobject (the attribute that tells the runtime which object is the graph) was either empty or hard-coded to #0050, which is only the root by convention. The header is now carried through from the file you opened. Across nine vanilla files — behaviour, character, project and skeleton, about 72,000 lines of XML — a save now differs from the same file put through the converter in 65 lines, four of the six distinct files matching exactly, and every one of them still converts back to a byte-identical binary. Which is the point: you can diff a save against a reference conversion and read the result.

- Saved XML is diffable against converter output again. Every param the editor wrote carried a `numelements=""` attribute, array or not — 18,884 of them in a single vanilla dragonbehavior.hkx — because the count field defaults to empty and nothing stopped the serializer from emitting it. The game never cared; XML→HKX conversion ignores an empty count. But it meant a file saved here differed from the same file converted by hkxconv on virtually every line, so diffing your save against a reference conversion — the usual way to check that an edit did what you meant and nothing else — drowned in noise. The attribute is now written only when there is a real count to write, and an array that is genuinely empty still says so explicitly with "0". Round-tripping vanilla dragonbehavior through save now reproduces exactly the same set of numelements attributes as Havok's own serializer, and cuts the remaining diff against converter output by two thirds.

- The Guide's live-debugger coverage grew from a button list into a real walkthrough. The Debugger tab section now describes the panel top to bottom — the status dot, the active-state cards, the 50-entry transition history, the variable list and its mount group, and the pop-out window — and three new Advanced sections sit alongside "Why Active States Are Empty". "Live Debugging: Setup & Connection" explains the two named pipes the editor and the SKSE plugin talk over, what each direction carries, that the client retries and reconnects on its own (so a red status line is a wait, not a failure), every moment the watch config is rebuilt and re-sent, and the trap behind most confusing sessions: state ids and variable indices are resolved by position against the file you have open, so open the Nemesis/Pandora output the game is actually running rather than your pre-patch source, or you get active states named "state 12" and variables that never flash. "Reading a Live Session" covers what the graph does by itself — the pulsing outline and ● LIVE badge, the green edge flash that tells you which of several candidate transitions really fired, the machine dropdown auto-following the actor and 🎯 pan-to-active chasing the node — plus the 0.001 change threshold that makes a variable flash, why some variable names are bright and others dim, how the actor icon is guessed, and when the 🐉 mount group appears. "Recording & Exporting a Session" writes down what the buttons never said: frames arriving while paused are dropped rather than buffered, a capture survives ⏹ but not ⏹ Stop Debug (export first), and the exported JSON is one object per snapshot with timestamp, actor, behaviour file, active states and variables — which is what makes it diffable against what your graph declares.

- Event ids and variable indices are pickers now, not numbers. Every event-id field in Object Data used to be a bare integer you had to look up by counting rows in the Events tab — a transition's eventId, the enterEventId/exitEventId of a trigger or initiate interval, a state machine's returnToPrevious / random / next-higher / next-lower ids, an event-driven modifier's activate/deactivate ids, and the id inside an event property, which is where notify events, clip triggers and event ranges keep theirs (436 of those in vanilla dragonbehavior alone). They now edit as a dropdown of this file's own event table, shown as name (#index), with (none) for -1; variableIndex, syncVariableIndex and assignmentVariableIndex get the same against the variable table, and params nested inside inline array elements are covered too. Havok publishes no metadata marking an int as a table index, so the editor goes by name (*EventId, assignmentEventIndex, and id on anything deriving from hkbEventBase) — checked against vanilla dragonbehavior: every int with an event- or variable-ish name is picked up, and nothing else is, so stateId, userData and the enums are untouched. An id your table doesn't cover shows as ‹unknown #N› and stays exactly as it was: the list always contains the current value, which is what makes it impossible for the dropdown to quietly blank a field. Edits run through the same path as typing, so undo/redo and the red-border validation behave identically.

- Event cross-reference, for one event or the whole table. New 🔗 Event Xref toolbar dialog: every event in the file with its listen/send counts, the references behind them, a filter for events nothing in the file references, double-click to jump to the referencing object, and 📋 Copy report for the clipboard. The Events tab's usage panel now runs the same scan, which is where the real fix is — it previously knew four kinds of site (transitions, wildcards, clip triggers, a short *EventId whitelist) and missed the rest: the enter/exit ids inside a transition's triggerInterval/initiateInterval sit a level below the transition, so a top-level param scan never saw them, and state enterNotifyEvents/exitNotifyEvents plus every send site (eventToSend, eventToSendWhenStateOrTransitionChanges, clip annotation triggers) were invisible too. An incomplete cross-reference is worse than none — you conclude an event is unused when it isn't — so every hit is now tagged ◀ listens or ▶ sends and named with its owning machine and state. "Unreferenced" stays a lead rather than a verdict, and says so: annotation events (HitFrame, SoundPlay.*, the dragon spell-fire events) fire from tracks inside the animation .hkx files, and cross-behaviour events are matched by name in another file's table — neither is visible from one behaviour graph, so an unreferenced event is never safe to delete on that basis alone.

- The Transitions tab detail panel actually shows the transition now. Everything below the flag badges used to be read off the hkbBlendingTransitionEffect the transition points at, and that object carries only duration, blendCurve, endMode and toGeneratorStartTimeFraction — priority, the nested-state routing, the condition and both intervals all live on the hkbStateMachineTransitionInfo itself, so those rows silently never rendered and the "when it fires" sentence quietly dropped its "and its condition is true" half. A transition with no effect at all (null, normal for a snap transition) short-circuited the whole panel down to the event row. All of it now reads from the transition struct, and toNestedStateId — the field that makes two transitions with the same destination state land on different sub-branches, e.g. a dragon's breath vs fireball shout — resolves through the destination state's nested machine into a clickable state name instead of a bare number, with variable indices in conditions resolved to names and both intervals listing their enter/exit events and times.

- Skyrim LE (32-bit) files open, save and convert. LE and SE share the same Havok schema (hk_2010.2.0-r1, class version 8) and differ only in packfile pointer size, so the editor now reads either one, offers both editions in Save (source edition first, and the status bar names the edition the open file came from), and a 🔄 LE ⇄ SE toolbar command repacks single files or whole folder trees in either direction — no external converter, no XML round-trip, originals untouched and results written to a folder beside the source, named after it (Behaviors → Behaviors_LE), with files already in the target edition copied across so the output is a complete, drop-in copy. The bundled HKX2Library had been de-generalised to SE: its 588 generated classes were dumped from the 64-bit runtime with 908 padding constants baked to an 8-byte pointer. tools/hkx-layout-gen re-derives Havok's layout rules from the metadata each class already carries and re-emits that padding as des.Padding(pad64, pad32), refusing to emit anything it can't first reproduce byte-for-byte at 64-bit — so SE output is unchanged by construction. Two real bugs fell out on the way: hkUlong members (hkbNode.m_userData, on every behaviour node) were read as a fixed 64-bit integer rather than a pointer-sized one, and ALIGN_16 members weren't honoured where the 64-bit layout happened to be 16-aligned already. Validated against all 180 loose vanilla LE files: all parse, and all convert to SE and back with byte-identical Havok XML. Nineteen classes still have no 32-bit layout (hkp* physics/ragdoll, type-metadata-only classes, and hkbGeneratorSyncInfo with its pre-existing SE over-read); none occur in behaviour, character, project, skeleton or animation files, and writing LE is refused with the class names listed rather than producing a silently corrupt file.

- Type-aware property editing, validated saves, and array element add/remove in Object Data. The panel now knows each param's declared Havok type (a new HavokTypeCatalog reflects the bundled HKX2 class set at load; enums declared as bare ints are detected via each class's serialized defaults): bools get a real checkbox by declared type instead of value-sniffing, enums a fixed-choice dropdown, and numeric fields live red-border validation with an "expected …" tooltip — range-aware (int8 = −128…127), nested inline params included, flags fields still accept their pipe-joined member names (FLAG_RAGDOLL|0x4c0 style, matching HKX2's ReadFlag exactly — zero false positives across vanilla behaviors). Save runs the same type check first: HKX saves are blocked with a list naming each bad value instead of dying deep in HKX2 with a bare FormatException (which also used to leave the corrupt .tmp.xml on disk — now cleaned up), XML saves warn and offer save-anyway, and ✓ Validate reports type errors too. Editing arrays by hand is finally safe: numelements recounts on every interactive edit (HKX2 treats it as authoritative — a stale count silently truncated the array on conversion), and editing a cached single ref (#-value params like generator) actually sticks now, including setting it to null — the resolved-ref cache re-resolves from the typed tokens instead of the getter silently snapping back to the stale id. And inline-struct arrays (event property arrays, transition arrays, notify events, binding sets…) get a generic ＋ Add element / per-element ✕ — new elements built from HKX2 class defaults, type-annotated, numelements maintained, undoable. Direct response to the 2026-08-02 external feedback round ("the property editor isn't type safe or even type aware… I can put anything I want in this box and it just yolo saves it").

- The graph actually graphs arbitrary Havok XMLs now. Four fixes from the same feedback round ("you just get isolated disconnected nodes"): ref arrays split on all whitespace, so Havok's line-wrapped #ref lists no longer silently drop states and transitions; the generator drill-down and behavior tree follow every #ref generically instead of a six-name param whitelist, so Bethesda classes (BSBoneSwitchGenerator's pDefaultGenerator/ChildrenA, BSSynchronizedClipGenerator's pClipGenerator, …) are no longer dead ends — 16 invisible bone-switch subtrees in vanilla magicbehavior alone; shared children keep every inbound edge (Havok graphs are DAGs — a modifier or binding set used by five parents now shows all five edges instead of looking owned by the first); and files without a state machine (ragdolls, skeletons, arbitrary Havok XML) seed the graph from the file's declared root instead of a silently blank canvas, with the walk descending into inline hkobjects so the root container's namedVariants actually connect. The behavior tree also stops duplicating nested state machines at top level.

- The Events tab kept a second array silently broken — fixed, plus a smarter Validate. Adding an event only appended the name; the matching hkbEventInfo record in hkbBehaviorGraphData.eventInfos was never created, and the game pairs the two arrays by index — so every event added through the tab was broken in-game (found in a user's real file during the capitto91 walkthrough: 30 names, 26 infos). Add/delete now insert/remove the info record at the same index (undo/redo included) and save reconciles the counts, which also repairs files desynced by older versions on their next save. ✓ Validate grew real teeth from the same session: eventNames/eventInfos and variableNames/variableInfos count mismatches are errors; a startStateId that doesn't match any state's stateId is an error naming the valid ids (the silent T-pose-on-activate case — machines using a start-state chooser or non-default startStateMode are skipped); the broken-reference and orphan scans now see refs inside inline structs (killing the false "orphaned object" on hkbBehaviorGraph in every file, and reporting genuinely broken refs inside transition arrays with indexed paths like transitions[2].transition); and ref parsing is whitespace-safe for line-wrapped arrays. Vanilla behaviors validate to zero issues; a hand-built test file reports exactly its real problems.

- Load → "✨ New behavior file…". Scaffolds a minimal valid behavior — hkRootLevelContainer → hkbBehaviorGraph → graph data / string data / variable value set → empty root hkbStateMachine — via a new BehaviorTemplateFactory that builds default HKX2 instances, links them, and serializes through HKX2's own XmlSerializer. That guarantees the exact dialect the rest of the pipeline speaks: ids start at #0050 with the root container first (matching the hard-coded toplevelobject in SerializeToFile), correct signatures, and vanilla sentinels set explicitly (all SM event ids and syncVariableIndex -1, maxSimultaneousTransitions 32; the enum zero-defaults are already the vanilla choices). User picks path + format (XML or SE HKX via the usual XmlToHkxAsync), then the file is opened through LoadFileAsync so editor state is identical to opening a real file — recents, undo stack, graph, everything. Round-trip verified: template XML → SE HKX binary → PackFileDeserializer, structure intact. Kills the "gut a vanilla file, lose the root scaffolding" trap from the capitto91 walkthrough. New Guide section "Creating a New Behavior File"; Getting Started and the behavior-reference section now point at it.

- Graph tab → right-click a state → "🔗 New behavior reference…". Creates an hkbBehaviorReferenceGenerator — the bridge node for Nemesis/Pandora-style patches that link a custom behavior file into a vanilla graph — and points that state's generator at it in one undoable action, same flow as the clip generator: replace-confirmation if the state already has one, wired through Children/InnerObject at creation so it survives the orphan-pruning .hkx save. New Guide section "Referencing Another Behavior File" covers the events-link-by-name rule and the sharp edges (typo'd path = silent T-pose in-game, not an error; the referenced file needs its own valid root scaffolding).
